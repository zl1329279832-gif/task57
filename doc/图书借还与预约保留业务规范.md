## 1. 状态机定义

### 1.1 预约状态机（Reservation Status — 五态）

预约状态定义在 `Reservation.java` 中，以 `static final byte` 常量表示：

| 值 | 常量名 | 中文含义 | 说明 |
|----|--------|----------|------|
| 0 | `STATUS_WAITING` | 排队中 | 读者已创建预约，在队列中等待到书 |
| 1 | `STATUS_RESERVED` | 已保留（到书保留中） | 图书已归还，为该读者保留，72 小时内可来取书 |
| 2 | `STATUS_FULFILLED` | 已完成（已借走） | 读者在保留窗口内成功借走图书 |
| 3 | `STATUS_CANCELLED` | 已取消 | 读者或管理员主动取消预约 |
| 4 | `STATUS_EXPIRED` | 已过期 | 72 小时保留窗口到期，读者未来取书 |

**状态转移图：**

```
                  ┌─────────────────────────────────────────────┐
                  │               创建预约                       │
                  │          /reservation/create                 │
                  ▼                                              │
            ┌───────────┐                                        │
            │  WAITING  │ (status=0, 排队中)                      │
            │  排队中    │                                        │
            └─────┬─────┘                                        │
                  │                                              │
          ┌───────┼────────────────┐                              │
          │       │                │                              │
          │  triggerReservation    │  cancelReservation            │
          │  (还书触发)            │  (读者/管理员取消)             │
          ▼                       ▼                              │
    ┌───────────┐          ┌───────────┐                          │
    │ RESERVED  │          │ CANCELLED │ (status=3, 终态)          │
    │ 已保留     │          │ 已取消     │                          │
    │ 72h窗口    │          └───────────┘                          │
    └─────┬─────┘                                                │
          │                                                      │
    ┌─────┼─────────────────────┐                                │
    │     │                     │                                │
    │  consumeReservation    72h到期(懒检测)                       │
    │  (保留人借走)           expireAndAdvance                     │
    ▼                        ▼                                   │
┌───────────┐         ┌───────────┐                              │
│ FULFILLED │         │  EXPIRED  │ (status=4)                    │
│ 已完成     │         │  已过期    │                              │
│ (终态)     │         └─────┬─────┘                              │
└───────────┘               │                                    │
                            │  triggerReservation                 │
                            │  (顺延给队列中下一位)                │
                            └────────────────────────────────────┘
                                     (若队列中还有 WAITING)
```

**补充说明：**

- **CANCELLED 路径中的顺延**：如果被取消的预约状态是 `RESERVED`（即当前保留人主动取消），系统会自动调用 `triggerReservation` 将保留名额顺延给队列中的下一位 WAITING 读者。
- **EXPIRED 的检测方式**：过期并非由定时任务驱动，而是在借书操作时**懒检测**（lazy evaluation）——当有人尝试借阅时检查 `expiryTime < now()`，若已过期则调用 `expireAndAdvance()` 标记过期并顺延。

### 1.2 图书借阅状态机（isBorrowed — 三态）

图书借阅状态存储在 `book_info` 表的 `isBorrowed` 字段（`TINYINT`），定义在 `BookInfo.java` 的 `isborrowed` 属性上：

| 值 | 含义 | 说明 |
|----|------|------|
| 0 | 可借（Available） | 馆藏在架，任何读者均可借阅（需排除保留名额占用情况） |
| 1 | 已借出（Borrowed） | 已被某读者借出，未归还 |
| 2 | 已保留（Reserved-Hold） | 已归还但为预约队列中的排头读者保留，72 小时保留窗口中 |

**状态转移图：**

```
                       borrowBook (CAS: 0→1)
              ┌──────────────────────────────────────┐
              │                                      │
              │                                      ▼
        ┌───────────┐                          ┌───────────┐
        │ Available │                          │ Borrowed  │
        │ isBorrowed│                          │ isBorrowed│
        │   = 0     │                          │   = 1     │
        └───────────┘                          └─────┬─────┘
              ▲                                      │
              │              returnBook              │
              │          (无人排队时 CAS: 1→0)        │
              └──────────────────────────────────────┘
              ▲                                      │
              │                                      │  returnBook
              │                                      │  (有人排队时 CAS: 1→2)
              │                                      ▼
              │                                ┌───────────┐
              │      保留过期且无人排队          │ Reserved  │
              │      (最终回落到 0)              │ isBorrowed│
              │                                │   = 2     │
              │                                └─────┬─────┘
              │                                      │
              │           保留人借走 (CAS: 2→1)        │
              │                                      │
              └───────────────────────┐              │
                                      │              ▼
                                      │     ┌───────────────┐
                                      └─────│  Borrowed     │
                                            │  isBorrowed=1 │
                                            └───────────────┘
```

**合法的 CAS 转移路径汇总：**

| 转移 | 含义 | 触发场景 |
|------|------|---------|
| `0 → 1` | 可借 → 已借出 | 读者借书（无保留或保留已消费） |
| `1 → 0` | 已借出 → 可借 | 还书且预约队列为空 |
| `1 → 2` | 已借出 → 已保留 | 还书且预约队列有 WAITING 读者 |
| `2 → 1` | 已保留 → 已借出 | 保留持有人在 72h 内来借书 |

### 1.3 两个状态机的联动关系

```
还书完成
    │
    ├─ 预约队列为空 ──────→ isBorrowed: 1→0 (Available)
    │                        Reservation: 无变更
    │
    └─ 预约队列有 WAITING ─→ isBorrowed: 1→2 (Reserved-Hold)
                              Reservation: WAITING→RESERVED
                              设置 expiryTime = now + 72h
                                 │
                     ┌───────────┼───────────────┐
                     │           │               │
                  72h内来取    72h过期          主动取消
                     │           │               │
              isBorrowed: 2→1   RESERVED→EXPIRED  RESERVED→CANCELLED
              RESERVED→FULFILLED    │               │
                              triggerReservation  triggerReservation
                              (顺延下一位)        (顺延下一位)
```

## 2. 两条借还路径对比

系统中存在两套独立的借书/还书 API，分别位于 `BorrowController` 和 `ReservationController`。**这两条路径的行为差异是导致合作方绕过预约保留的根本原因。**

### 2.1 BorrowController — 基础路径（无预约感知）

- **前缀**：`/borrow`
- **未注入** `ReservationService`，完全不感知预约系统的存在

| 端点 | 方法 | 行为 |
|------|------|------|
| `/borrow/borrowBook` | GET | 检查 `isBorrowed==0` → CAS `0→1` → 插入 borrow 记录 |
| `/borrow/reader/borrowBook` | GET | 同上（reader 路径别名） |
| `/borrow/returnBook` | GET | CAS 设 returnTime → CAS `1→0` |
| `/borrow/reader/returnBook` | GET | 同上 |
| `/borrow/renewBook` | GET | 续借延期 |

**关键缺陷：**

1. **借书时不检查保留名额**：即使 `isBorrowed==0` 是因为还书后无人排队暂时可借，也不会检查是否存在 RESERVED 保留。但更关键的是——当还书走 `/borrow/returnBook` 时，`isBorrowed` 会被直接设为 0（而不是 2），**跳过 triggerReservation 流程**，WAITING 中的预约永远不会被触发。
2. **还书时不触发预约保留**：直接 CAS `1→0`，不调用 `reservationService.triggerReservation()`。队列中排队的读者将永远无法收到保留通知。
3. **馆员手工还书后保留窗口乱套**：如果馆员通过 `/borrow/returnBook` 执行手工还书，已有预约队列的图书会直接变为"可借"状态，任何人（包括非预约读者）都可以通过 `/borrow/borrowBook` 直接借走，完全绕过排队机制。

### 2.2 ReservationController — 增强路径（预约感知）

- **前缀**：`/reservation`
- **注入了** `ReservationService`、`BookInfoService`、`BorrowService`

| 端点 | 方法 | 行为 |
|------|------|------|
| `/reservation/borrowBook` | GET | 检查保留名额 → 懒过期检测 → 消费保留 → CAS 更新 → 插入 borrow |
| `/reservation/reader/borrowBook` | GET | 同上 |
| `/reservation/returnBook` | GET | CAS 设 returnTime → triggerReservation → CAS `1→2` 或 `1→0` |
| `/reservation/reader/returnBook` | GET | 同上 |

**增强行为：**

1. **借书时识别保留**：如果图书有 RESERVED 状态的预约，仅允许保留持有人借出；其他读者会收到"该书已被保留给其他读者，您暂不可借"的拒绝。
2. **借书时懒过期检测**：若保留已超过 72h 窗口，自动调用 `expireAndAdvance()` 标记过期并顺延。
3. **还书时触发保留**：还书后调用 `triggerReservation()` 查找队列头部的 WAITING 预约，将其提升为 RESERVED 并设置 72h 窗口；图书 CAS 从 `1→2`。
4. **支持 `isBorrowed==2` 状态借出**：当保留持有人来借书时，CAS 从原始状态（可能是 0 或 2）更新到 1。

### 2.3 行为差异汇总表

| 维度 | `/borrow/*` (BorrowController) | `/reservation/*` (ReservationController) |
|------|-------------------------------|------------------------------------------|
| 借书前检查保留 | **不检查** | 检查 RESERVED，非保留人拒借 |
| 借书 CAS 转移 | 仅 `0→1` | `originalStatus→1`（支持 `0→1` 和 `2→1`） |
| 还书后触发预约 | **不触发** | 调用 `triggerReservation()` |
| 还书 CAS 转移 | 仅 `1→0` | `1→2`（有预约）或 `1→0`（无预约） |
| 过期检测 | 无 | 借书时懒检测，调用 `expireAndAdvance()` |
| 续借 | 支持 `/renewBook` | 不提供（需走 `/borrow/renewBook`） |
| MAX_BORROW_LIMIT 检查 | 检查（5 本） | 检查（5 本） |
| CAS 幂等还书 | 支持 | 支持 |
| 事务管理 | `@Transactional` + 手动回滚 | `@Transactional` + 手动回滚 |

### 2.4 集成方应使用的 Canonical API

> **结论：集成方必须统一使用 `/reservation/*` 路径进行借书和还书操作。`/borrow/borrowBook` 和 `/borrow/returnBook` 仅作为遗留接口保留，不应在有预约需求的场景中使用。**

**推荐的 Canonical API 清单：**

| 操作 | Canonical 端点 | 说明 |
|------|----------------|------|
| 借书 | `GET /reservation/borrowBook?userid={}&bookid={}` | 带保留检查的借书 |
| 借书（reader路径） | `GET /reservation/reader/borrowBook?userid={}&bookid={}` | 同上 |
| 还书 | `GET /reservation/returnBook?borrowid={}&bookid={}` | 带预约触发的还书 |
| 还书（reader路径） | `GET /reservation/reader/returnBook?borrowid={}&bookid={}` | 同上 |
| 续借 | `GET /borrow/renewBook?borrowid={}` | 续借仍走 BorrowController（ReservationController 未提供） |
| 创建预约 | `GET /reservation/create?userid={}&bookid={}` | 图书不可借时排队 |
| 取消预约 | `GET /reservation/cancel?reservationid={}` | 读者取消 |
| 查看我的预约 | `GET /reservation/myList?userid={}` | 读者查看列表 |
| 查看预约队列 | `GET /reservation/queue?bookid={}` | 管理员查看 |
| 管理员取消预约 | `GET /reservation/admin/cancel?reservationid={}` | 管理员操作 |
| 管理员调整排位 | `GET /reservation/admin/adjustPosition?reservationid={}&newPosition={}` | 调整队列 |

**遗留接口（不推荐使用）：**

| 端点 | 风险 |
|------|------|
| `/borrow/borrowBook` | 绕过预约保留检查，可能占用保留名额 |
| `/borrow/returnBook` | 不触发 triggerReservation，导致预约队列永远无法推进 |

## 3. 还书 → 保留 → 过期顺延 → 消费保留 完整序列

### 3.1 时序图

```

      │  returnBook     │                            │                       │

      │   bookid)       │                            │                       │

      │                 │                            │                       │

      │                 │◄──────────── affected=1 ─────────────────────────┤

      │◄─── return 1 ──┤                            │                       │
      │   (还书成功)     │                            │                       │
```

### 3.2 各阶段详细说明

#### 阶段 1：还书（Return）

**入口**：`ReservationController.returnBook(borrowid, bookid)`

1. 验证图书和借阅记录存在。
2. 执行 CAS 还书：`borrowService.returnBorrowCas(borrowid)`。
   - SQL：`UPDATE borrow SET returnTime = #{returntime} WHERE borrowId = #{borrowid} AND returnTime IS NULL`
   - 若 `affected == 0`，说明已经还过，幂等返回成功（`return 1`）。
3. CAS 成功后进入阶段 2。

**源码位置**：`ReservationController.java:217-264`

#### 阶段 2：触发预约保留（triggerReservation）

**入口**：`reservationService.triggerReservation(bookid)`

1. 查询队列头部：`selectNextWaiting(bookid)` — 选出 `status=0 (WAITING)` 且 `queuePosition` 最小的预约记录。
2. 若队列为空（`next == null`）：返回 `null`，后续图书 CAS `1→0`。
3. 若找到等待者：
   - 设置 `status = STATUS_RESERVED (1)`
   - 设置 `reserveTime = now`
   - 设置 `expiryTime = now + HOLD_PERIOD_MS`（**HOLD_PERIOD_MS = 72 小时 = 259,200,000 毫秒**）
   - 更新数据库，返回被触发的预约对象。

**源码位置**：`ReservationServiceImpl.java:92-111`

**常量定义**：

```java
private static final long HOLD_PERIOD_MS = 72L * 60 * 60 * 1000;  // 72小时
```

#### 阶段 3：图书状态更新

根据 `triggerReservation` 的返回值：

| 返回值 | 图书 CAS | 结果 |
|--------|----------|------|
| `triggered != null`（有人排队） | `isBorrowed: 1 → 2` | 图书进入"已保留"，仅保留人可借 |
| `triggered == null`（无人排队） | `isBorrowed: 1 → 0` | 图书回到"可借"，任何人可借 |

#### 阶段 4：72 小时保留窗口

- 保留被触发后，读者有 **72 小时**（3 天）来馆取书。
- 系统不使用定时任务或后台线程主动检测过期。
- 过期仅在**下一次有人尝试借阅该书**时懒检测。

#### 阶段 5：过期顺延（expireAndAdvance）

**触发时机**：借书时检测到保留已过期（`expiryTime < now()`）。

**入口**：`reservationService.expireAndAdvance(reservationid)`

执行步骤：
1. 查询当前预约记录。
2. 将其状态标记为 `STATUS_EXPIRED (4)`。
3. 调用 `triggerReservation(bookid)` 为下一位 WAITING 读者生成保留。
4. 返回下一位读者的预约（若队列中仍有 WAITING），否则返回 `null`。

**懒检测的代码路径**（`ReservationController.borrowBook`）：

```
borrowBook(userid, bookid)
  ├─ isBorrowed == 0 && 存在 RESERVED 保留
  │    └─ expiryTime < now? → expireAndAdvance → 重新查询活跃保留
  │
  └─ isBorrowed == 1 或 2 && 该用户有 RESERVED 保留
       └─ expiryTime < now? → expireAndAdvance → 抛出"保留已过期，已顺延给下一位"
```

**源码位置**：`ReservationServiceImpl.java:114-128`

#### 阶段 6：消费保留（consumeReservation）

**触发时机**：保留持有人在 72h 窗口内来借书。

**入口**：`reservationService.consumeReservation(reservationid)`

执行步骤：
1. 将预约状态更新为 `STATUS_FULFILLED (2)`。
2. 控制器继续执行借书流程：CAS 更新 `isBorrowed: originalStatus → 1`，插入 borrow 记录。

**源码位置**：`ReservationServiceImpl.java:84-89`

#### 完整生命周期示例

```
时间线              事件                        Reservation.status    isBorrowed
────────────────────────────────────────────────────────────────────────────────
T0                 读者B预约图书X                WAITING(0)            1(已借出)
T1                 读者A还书(走增强路径)          RESERVED(1)           2(已保留)
                   → triggerReservation触发      expiryTime=T1+72h
T1 ~ T1+72h       72小时保留窗口                 RESERVED(1)           2(已保留)
  ├─ 场景A: 读者B在T2(T2<T1+72h)来借书
  │    → consumeReservation                     FULFILLED(2)          1(已借出)
  │    借书完成，预约生命周期结束
  │
  ├─ 场景B: 读者B未来取，读者C在T3(T3>T1+72h)尝试借书
  │    → 懒检测发现过期
  │    → expireAndAdvance                       EXPIRED(4)
  │    → triggerReservation(下一位读者D)          读者D: RESERVED(1)    2(仍保留)
  │
  └─ 场景C: 读者B主动取消预约
       → cancelReservation                      CANCELLED(3)
       → triggerReservation(下一位读者D)          读者D: RESERVED(1)    2(仍保留)
```

## 4. 借阅上限（MAX_BORROW_LIMIT）

```java
private static final int MAX_BORROW_LIMIT = 5;
```

- **定义位置**：`BorrowController.java:29`、`ReservationController.java:30`（两处独立定义，值相同）。
- **含义**：每位读者同时持有的未归还借阅记录不得超过 5 条。
- **统计 SQL**：

```sql
SELECT COUNT(*) FROM borrow
WHERE userId = #{userid} AND returnTime IS NULL
```

- **检查时机**：在**借书操作的最前端**，查询通过后才执行后续 CAS 和保留检查。
- **超限行为**：抛出 `NotEnoughException("您当前借阅数量已达上限（5本）")`，接口返回 `0`。

**注意**：预约数量**不受**此限制约束。读者即使已借满 5 本，仍可创建预约排队；但在预约保留触发后尝试取书借阅时，如果仍持有 5 本未还，会被借阅上限拦截。

## 5. CAS 并发控制与失败策略

### 5.1 CAS 操作一览

系统使用数据库层面的 **Compare-And-Swap** 实现乐观并发控制，通过 SQL `WHERE` 子句的前置条件实现原子性判断。

#### CAS 操作 1：图书状态更新（casUpdateIsBorrowed）

```sql
UPDATE book_info
SET isBorrowed = #{newStatus}
WHERE bookId = #{bookid}
  AND isBorrowed = #{expectedStatus}
```

- **原子性保障**：MySQL InnoDB 行级锁确保 `WHERE` 条件匹配与 `SET` 更新在同一临界区内完成。
- **返回值**：`affected rows`。若为 0 表示 `expectedStatus` 与实际值不匹配（被其他事务抢先修改）。

**源码位置**：`BookInfoMapper.xml:193-198`

#### CAS 操作 2：借阅记录归还（returnBorrowCas）

```sql
UPDATE borrow
SET returnTime = #{returntime}
WHERE borrowId = #{borrowid}
  AND returnTime IS NULL
```

- **目的**：幂等还书——同一笔借阅只能还一次。
- **返回值**：`affected rows`。若为 0 表示已经还过。

**源码位置**：`BorrowMapper.xml:146-151`

### 5.2 CAS 失败时的处理策略

本系统采用**单次尝试、不自动重试**的策略。CAS 失败后的具体行为如下：

| CAS 操作 | 控制器 | 失败含义 | 失败处理 |
|----------|--------|---------|---------|
| `casUpdateIsBorrowed(0→1)` | BorrowController | 图书已被其他读者借走 | 抛出 `NotEnoughException`，事务回滚，返回 `0` |
| `casUpdateIsBorrowed(0→1)` | ReservationController | 图书状态已变更 | 抛出 `NotEnoughException("状态已变更，请重试")`，事务回滚，返回 `0` |
| `casUpdateIsBorrowed(2→1)` | ReservationController | 保留状态已变更 | 同上 |
| `casUpdateIsBorrowed(1→0)` | BorrowController | 图书状态不一致 | 抛出 `OperationFailureException`，事务回滚，返回 `0` |
| `casUpdateIsBorrowed(1→2)` | ReservationController | 还书并发冲突 | 抛出 `OperationFailureException`，事务回滚，返回 `0` |
| `casUpdateIsBorrowed(1→0)` | ReservationController | 还书并发冲突 | 抛出 `OperationFailureException`，事务回滚，返回 `0` |
| `returnBorrowCas` | 两个 Controller | 已经还过 | **视为成功**，幂等返回 `1` |

**对集成方的影响**：

- 借书接口返回 `0` 时，客户端应提示用户稍后重试（用户侧重试），而非自动循环重试。
- 还书接口在 CAS 幂等保护下是天然幂等的，重复调用安全。
- 所有 CAS 失败均在 `@Transactional` 事务中通过手动 `setRollbackOnly()` 回滚，确保部分写入不会残留。

**为什么不自动重试**：

1. `casUpdateIsBorrowed` 失败通常意味着**业务状态已不满足前提条件**（书已被借走 / 已被其他人操作），自动重试不会改变结果。
2. 对于真正的瞬时并发竞争（如两人同时借同一本书），单次 CAS 足以保证只有一个人成功，另一人收到明确失败提示后由用户决策是否重试。
